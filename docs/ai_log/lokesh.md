- **Tool/model:** Claude Code (Sonnet 5)
- **What it contributed:** Wrote `src/download.py` (sec-edgar-downloader, `download_details=True`, user agent from `params.yaml`) and a regex-based unpacker for EDGAR's SGML `full-submission.txt` format, confirmed against a real Apple 10-K fetched from `data.sec.gov`/`www.sec.gov` directly. - **How verified:** Ran both scripts end-to-end against live EDGAR for AAPL 10-K/10-Q in the `params.yaml`-pinned date range (2024-01-01 to 2026-08-01): 11 filings downloaded and unpacked, 11 PDFs rendered. Checked `data/raw` size (76M, under the 100M acceptance cap), confirmed all 11 `unpacked/` folders contain a `.xsd`, cross-checked rendered page counts with `pdfinfo` against each filing's own printed page count in its signature-page footer (e.g. the FY2025 10-K's PDF has 61 pages against a footer reading "page 58" + cover/signature pages), and spot-checked `Item 1`–`Item 16` headings are all present in extracted text.
- **Failure/limitation found:** First run kept both `full-submission.txt` and the separately-fetched `primary-document.html` alongside the unpacked documents, pushing `data/raw` to 140M — over the 100M acceptance limit. Fixed by deleting `full-submission.txt` after unpacking, since every byte of it is already reproduced under `unpacked/`. Also caught a red herring: the `file` CLI reported "8 pages" for the rendered 10-K PDF, which looked like a rendering bug (font-size/CSS causing text to pile onto too few pages); `pdfinfo` (poppler) reported the correct count (61), so `file`'s page-count parsing for this PDF's xref structure isn't reliable — don't trust it for this check.
- **Confidence statement:** High confidence the acceptance criteria are met (sizes and counts above are measured, not estimated). Lower confidence in the long-term shape of `unpacked/` — once Part 1/2/3 start parsing specific documents inside it, their owners may want it split differently (e.g. separating the primary document from XBRL linkbase files); this script only guarantees every embedded document lands under `unpacked/` by its EDGAR filename.

## 2026-10-03 — Follow-up: code review (8 finder angles, high effort)

- **Tool/model:** Claude Code (Sonnet 5), 8 parallel review subagents + manual verification
- **What it contributed:** Reviewed the full diff for correctness, reuse, simplification, efficiency, altitude, and conventions. Two of the most-repeated candidate findings — "re-running `download.py` crashes because it deleted `full-submission.txt`" and "`count == 0` raises on a harmless re-run" — were empirically refuted by actually re-running the script against already-processed data (sec-edgar-downloader checks file existence per-file, so a deleted file is simply re-fetched; `count` reflects total filings matched, not newly-downloaded ones). A "binary content gets corrupted by `read_text(errors='replace')`" claim was also refuted by decoding a real `.zip` exhibit — EDGAR uuencodes all binary content as ASCII, so it's never actually binary at that layer.
- **Fixes applied:** (1) `src/render.py` now reads each PDF's actual page size back via `pypdf` instead of trusting a static `{"Letter": (612, 792)}` table — a live Playwright test showed a filing with `@page{size:landscape}` CSS silently flips the real output while the old code kept logging portrait dimensions. (2) `manifest.csv` is now written incrementally (row per filing) instead of once at the end, so one bad filing no longer discards manifest rows for every filing already rendered. (3) The primary document is no longer unpacked into `unpacked/` since `primary-document.html` (from `download_details=True`) already holds it — was being stored twice, confirmed byte-identical via `diff`. (4) `unpack_submission()` now rejects duplicate `<FILENAME>` values and uses `rindex` instead of `index` for `</TEXT>` so embedded escaped markup can't silently truncate a document. (5) `submission_path.unlink()` moved out of `unpack_submission()` into the caller, so disk-budget cleanup isn't hidden inside a function whose job is just parsing. (6) `stem_for()` moved to a new `src/contracts.py` since `docs/CONTRACTS.md` already declares cross-stage helpers should live in a named shared module. (7) Added a form-string `/` guard and a download-time check that `download_details` actually produced a `primary-document.*` file, instead of only discovering it later in `render.py`. (8) Commented why `params.yaml`'s `before` date is pinned, so a teammate re-running next month doesn't mistake it for a stale/broken download.
- **How verified:** Re-ran the full pipeline end-to-end after all fixes (`rm -rf data/raw data/rendered`, fresh download + render): 11 filings, 11 PDFs, manifest now logs real page sizes (612.0×792.0 for all current filings — none are landscape), `data/raw` dropped from 76M to 66M after removing the primary-document duplication.
- **Confidence statement:** High confidence the fixes are correct for the current AAPL 10-K/10-Q corpus — verified by re-running, not just reading the diff. Lower confidence on three forward-looking, currently-dormant edge cases that were flagged but not fixed (no filing in this corpus triggers them): a form string containing `/` (e.g. `ATS-N/UA`) would still break the one-folder-per-form path assumption if `params.yaml` ever added such a form; amended filings (`include_amends`) aren't handled; and the `</TEXT>`/duplicate-filename guards are defensive (no real filing has hit them yet).
